# Prompt Maker

Rewrite a raw user instruction into a structured, project-grounded instruction file, then execute the task from that file. The file is the contract: it is what the agent works from, updates as reality diverges, and leaves behind as a record of what was asked and how it was interpreted.

## When to Activate

Activate on explicit invocation (`/prompt-maker`) or when the user asks to optimize/structure/formalize a prompt. Do not activate on ordinary instructions, even messy ones, unless the user names the skill or asks for prompt optimization — the skill changes how the request is executed, so it must not trigger itself.

## Workflow

### 1. Scan the project

Gather the context the rewritten instruction will be grounded in. Read only what exists and is relevant:

- Project docs: README, AGENTS.md / CLAUDE.md / similar instruction files
- Manifests and config: package.json / pyproject.toml / Cargo.toml / pom.xml / etc.
- Structure: top-level directory layout, then targeted files where the task will land
- Git state, if a repo: current branch, recent commits, uncommitted changes

Extract only facts relevant to the instruction at hand: stack, conventions, existing patterns to follow, constraints that bound the task. Do not dump the whole scan into the file.

### 2. Analyze the raw instruction

From the user's prompt, extract:

- **Intent** — the outcome the user wants, in one sentence
- **Explicit requirements** — everything the prompt literally asks for
- **Implicit assumptions** — things the user clearly expects but did not state
- **Ambiguities and conflicts** — unclear scope, contradictions, or requests that clash with project reality discovered in the scan

If a question is genuinely blocking (cannot proceed without the answer), ask the user before writing the file. If it is not blocking, record it with the assumption you will proceed on — never silently guess and never stall on questions the task can survive without.

### 3. Write the instruction file

Write `PROMPT.md` at the project root. If `PROMPT.md` already exists and was not generated by this skill (no `<!-- prompt-maker -->` marker), write `PROMPT-<task-slug>.md` instead so an unrelated file is never overwritten. Structure:

```markdown
<!-- prompt-maker: <date> -->

# <Task title>

## Goal
<One sentence: the outcome, and what done looks like.>

## Context
<Verified project facts this task rests on — stack, relevant files with paths, conventions to follow. Facts only, nothing speculative.>

## Requirements
<Numbered, concrete, testable. Each requirement traces to something the user asked for or an assumption recorded below.>

## Non-goals
<Explicitly out of scope, so adjacent work is not dragged in.>

## Assumptions
<Each implicit assumption and each unresolved ambiguity, with the choice being made to proceed. Format: "Assumed X; say the word to change it.">

## Plan
<Ordered steps, each small enough to verify before the next.>

## Verification
<How completion will be checked: commands to run, outputs to observe.>

## Status
<Not started | In progress — step N | Blocked | Done>
```

Keep the file lean — it is an execution contract, not an essay. Drop sections that genuinely have no content rather than padding them.

### 4. Execute from the file

Treat the file as the authoritative instruction set and work through its Plan. Rules during execution:

- Follow the file's steps in order; verify each step against the file's Verification section as you go.
- Update **Status** as work progresses — the file must always reflect where things stand.
- If execution reveals the file is wrong (a false assumption, a missed dependency, scope that needs to change), update the file first, note what changed and why in **Assumptions**, then continue. Do not silently deviate from the contract.
- Blocking discoveries (the task cannot proceed without a user decision) pause execution at the current step and set Status to Blocked with the question stated.

### 5. Wrap up

When done, set Status to Done and report: what was executed, which assumptions were exercised, and where the file is. Leave the file in place — it is the record of the interpretation; the user deletes it if unwanted.

## Hard Constraints

- Never add a requirement the user did not ask for or that does not follow from a recorded assumption. Structuring is reorganization, not scope expansion.
- The user's intent is fixed; only its expression is optimized. If the prompt is internally contradictory, resolve via a question or a recorded assumption — never by picking one side silently.
- The file is the single source of truth during execution. Any agent acting in this session after the file exists works from the file, not from memory of the original prompt.
